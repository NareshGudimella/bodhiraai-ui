# bodhiraai-ui: production deployment

How the Next.js web app runs in production: **one Cloudflare Worker** (`ba-ui`) on `bodhiraai.com`. The Worker routes the API, serves the legacy files and private files from R2, and runs the Next.js app itself through the [OpenNext Cloudflare adapter](https://opennext.js.org/cloudflare) (`@opennextjs/cloudflare`). There is no container and no Docker. The steps for switching from legacy are in [../docs/cutover-runbook.md](../docs/cutover-runbook.md).

The same code also runs on a plain Node host (Hostinger) with `npm run build` and `npm run start`. See §8.

> **Status: draft for review.** None of this has been deployed to Cloudflare yet. It was built, previewed locally in workerd and dry-run deployed (§6).

## 1. Pieces

| Piece | Where | What it does |
|---|---|---|
| `worker/index.ts` | the Worker entry (`main` in `wrangler.jsonc`) | Edge routing (below), then hands every other request to the OpenNext handler (`.open-next/worker.js`, generated by `npm run cf:build`). Re-exports the cache Durable Objects |
| `worker/file-sig.ts`, `worker/legacy-key.ts`, `worker/body-limit.ts` | pure helpers | Signed links, legacy R2 keys, per-path body limits. Tested in `worker/test/` (`npm run test:worker`) |
| `open-next.config.ts` | OpenNext settings | The Next cache: R2 incremental cache, Durable Object tag cache and queue (§3) |
| `wrangler.jsonc` | Worker config | Bindings, vars, secret names, and the three targets: top level (`no-route`), `env.production`, `env.staging` |
| `security-headers.mjs` | shared | Legacy's security headers and CSP. `next.config.mjs` sends them on every response from Next; `scripts/cf-assets-headers.mjs` writes them to `.open-next/assets/_headers` for static files |
| Static assets | `.open-next/assets` (binding `ASSETS`) | `public/` and `_next/static`. Cloudflare serves them **before** the Worker runs; `_next/static` is cached as immutable |
| R2 `bodhira-legacy` | bound as `LEGACY_FILES` | Legacy uploads (`media/…`, `cloud/…`) and the site's `.mp4` videos (`assets/…`), copied before cut-over |
| R2 `bodhira-private` | bound as `PRIVATE_FILES`; the API's `R2_PRIVATE_BUCKET` | Every non-public upload (avatars, school logos, lesson files and thumbnails, assignment attachments, submissions, recordings). **Never public**: no `r2.dev` URL, no custom domain. Reached only through signed `/files/*` links (security: not in legacy) |
| R2 `bodhiraai-web-opennext-cache` | bound as `NEXT_INC_CACHE_R2_BUCKET` | Next's cache entries. Never public |
| R2 uploads bucket | the API's `R2_BUCKET` / `R2_PUBLIC_URL` | Public uploads (marketing site / CMS files only), as absolute URLs. Not used by the Worker |

What the Worker does with each request ([worker/index.ts](worker/index.ts)):
- **`/api/v1/*`, `/webhooks/*`:** passed to `API_ORIGIN` (Elastic Beanstalk), streamed, with `X-Client-IP` and `X-Proxy-Secret`. The mobile app and the gateway webhook URLs stay the same.
- **`/media/*`, `/cloud/*`, `/assets/**.mp4`:** served from `LEGACY_FILES`, with byte ranges so videos can be seeked. `/media/invoices/…` (any letter case, also percent-encoded) answers 404: invoices live only in the private bucket, behind the authenticated invoice endpoints (security: not in legacy).
- **`/files/<key>?exp&sig`:** private files from `PRIVATE_FILES`, only with a link the API signed ([worker/file-sig.ts](worker/file-sig.ts)): `sig` is base64url HMAC-SHA256 with the file-urls key derived from `APP_SECRET` over `"<decoded key>\n<exp>"`. A missing or wrong signature, an expired link, `exp` more than 24 h ahead, or a forbidden key (`invoices/…`, `..`, `\`, empty segments) answers 403 `{"message":"Link expired or invalid."}`; a missing object 404. Byte ranges as for `/media`. Headers: `Content-Disposition: inline`, `nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: private, max-age=<seconds until exp, ≤ 3600>`. Locally the API serves `/files/*` itself on :4000. (security: not in legacy)
- **R2 responses** get `nosniff`, and anything that isn't a PDF, video or audio file also gets `Content-Security-Policy: default-src 'none'; sandbox`, so a stray HTML or SVG upload can't act as the site.
- **Body limits:** non-API requests over their path's limit answer 413 (§7).
- **Everything else:** the Next.js app, in the same Worker. The visitor's IP goes along as `X-Client-IP`, set by the Worker so a visitor can't supply their own; `api()` forwards it to the API with `X-Proxy-Secret`.

## 2. Settings

| Setting | Where | Value |
|---|---|---|
| `API_ORIGIN` | `wrangler.jsonc` vars | `https://api-origin.bodhiraai.com` |
| `SITE_URL` | `wrangler.jsonc` vars | `https://bodhiraai.com` |
| `API_URL`, `LEGACY_URL` | derived in `worker/index.ts` (`nextEnv`) | `${API_ORIGIN}/api/v1` and `SITE_URL` (the Worker serves the legacy files on the site's own domain). The Next server code reads them from `process.env`; OpenNext fills `process.env` from the Worker's string bindings. Set them as vars only to override |
| `APP_SECRET` | `npx wrangler secret put APP_SECRET` | **The API's `APP_SECRET`, the same value.** The Worker and the Next server derive two keys from it with HKDF-SHA256: the proxy header `X-Proxy-Secret` (info `bodhira:proxy`; sent on proxied API calls and by the Next server on its own calls, `lib/proxy-secret.ts`) and the signed-file key (info `bodhira:file-urls`). A wrong value gets the API's calls refused and every signed link answered 403. Rotating it changes both keys, so change the API's and the Worker's together (links already handed out break; they last 30 minutes, `FILE_URL_TTL`) |

`APP_SECRET` is listed under `secrets.required` in `wrangler.jsonc` (name only, no value). Locally it comes from `.dev.vars` (copy `.dev.vars.example`; git-ignored).

## 3. Caching

`cacheComponents` is on, and the marketing site's public data is cached with `'use cache'` under tag `site` (`lib/site-api.ts`, `cacheLife('minutes')`). Web Studio saves call `updateTag('site')`. In `open-next.config.ts`:

| Part | Choice | Why |
|---|---|---|
| Incremental cache | R2 (`bodhiraai-web-opennext-cache`), with the colo's Cache API in front (`short-lived`: a regional copy is reused for at most a minute, and the tag cache is still checked on every hit) | Shared by every isolate in every location. `'use cache'` entries are stored as `….composable` objects |
| Tag cache | Sharded Durable Object tag cache (`DOShardedTagCache`, binding `NEXT_TAG_CACHE_DO_SHARDED`, 4 shards) | Strongly consistent, so `updateTag('site')` / `revalidateTag` after a save is seen by every isolate on its next read. It's a "next mode" tag cache, which `'use cache'` needs. Needs no D1 database to create |
| Queue | Durable Object queue (`DOQueueHandler`, binding `NEXT_CACHE_DO_QUEUE`) | Background revalidation of stale ISR entries, deduplicated across isolates. It calls the Worker back through `WORKER_SELF_REFERENCE` |
| Cache purge | none | Nothing is cached in Cloudflare's CDN: pages render per request and send `private, no-store` |

This is a change from the container design, where a save refreshed the cache only in the container that handled it: the site cache is now shared (not in legacy). The Durable Objects are created by the `v1` migration on the first deploy. `npm run cf:deploy` first uploads the build's prerendered cache entries to the R2 bucket, then runs `wrangler deploy`.

## 4. Deploy

Deploys run in GitHub Actions, never from a workstation.

- **CI** (`.github/workflows/ci.yml`, every push): lint, type-check, the plain `npm run build` (the Hostinger path), the Worker tests, `npm run cf:build`, the Worker type-check, and `wrangler deploy --dry-run` for all three targets.
- **Deploy** (`.github/workflows/deploy.yml`, manual): Actions → Deploy → Run workflow, on a commit CI passed. It runs `npm run cf:build`, then `npm run cf:deploy -- --env <target>`. Choose the target:

  | Target | Config | Route | When |
  |---|---|---|---|
  | `no-route` (default) | `wrangler.jsonc`, top level (`--env=`) | **none**: no production traffic; `*.workers.dev` only | Before cut-over |
  | `production` | `--env production` | `bodhiraai.com/*` | Cut-over step 7 ([runbook](../docs/cutover-runbook.md) §6), then every deploy |
  | `staging` | `--env staging` | the staging host | The rehearsal (runbook §4) |

  `no-route` and `production` deploy the same Worker (`ba-ui`), so its secrets, Durable Objects and cache carry over to cut-over. A `no-route` deploy never removes a route (wrangler only replaces routes when the config lists some), so after cut-over it would still update production code: use `production` from then on. Wrangler doesn't inherit bindings or vars into an env, so change the top level, `env.production` and `env.staging` together.

Deploy the API first whenever a release changes both apps.

### One-time setup (the owner, before the first deploy)

1. **Plan:** Workers **Paid** on the account (the Free plan's 10 ms CPU per request and 3 MiB bundle limit don't fit a Next.js server; see §7). Decide the zone plan from the upload size (§7).
2. **GitHub:** in the repository settings, create the `production` environment with a required reviewer (used by `no-route` and `production`), and `staging` for the rehearsal. Add to each the secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. Token permissions: Account → Workers Scripts: Edit, Workers R2 Storage: Edit; Zone `bodhiraai.com` → Workers Routes: Edit (staging: its own zone).
3. **Buckets and secrets**, from any machine with Node (in `bodhiraai-ui/`, after `npm ci`):
   ```bash
   npx wrangler login
   npx wrangler r2 bucket create bodhira-legacy
   npx wrangler r2 bucket create bodhira-private     # leave public access off
   npx wrangler r2 bucket create bodhiraai-web-opennext-cache   # leave public access off
   npx wrangler secret put APP_SECRET                # the API's value; also on rotation
   ```
   The secrets belong to the Worker `ba-ui`, shared by `no-route` and `production`. `wrangler secret put` before the first deploy creates the Worker with no code yet; alternatively deploy `no-route` first and then set them (the site answers errors until they're set). The Durable Objects need no setup.
4. **Legacy files:** copy them into `bodhira-legacy` under the same paths (runbook §3).
5. **DNS:** `bodhiraai.com` must be proxied (orange cloud) before the `production` target is run. The route is `bodhiraai.com/*` in `env.production` only; `www` gets a 301 Redirect Rule to the apex instead (§5, "One canonical host"). `api-origin.bodhiraai.com` is a proxied record to the Beanstalk load balancer (runbook §5). No custom domain on the Worker: the route on the existing zone is enough.
6. **Staging:** replace the `<placeholders>` in `env.staging` of `wrangler.jsonc` (host, zone, API origin), create `bodhira-legacy-staging`, `bodhira-private-staging` and `bodhiraai-web-opennext-cache-staging` (public access off), and set the staging secret with `--env staging` (the staging API's `APP_SECRET`). Never point it at production buckets or the production API.

## 5. Behaviour behind Cloudflare

- **Security headers:** legacy's `SecurityHeaders` values are applied to every response: `nosniff`, `X-Frame-Options: SAMEORIGIN`, Referrer-Policy and Permissions-Policy. Production builds also get HSTS and legacy's CSP. Pages from Next get them from `next.config.mjs`; static files (served by Cloudflare before the Worker) from `.open-next/assets/_headers`, which `npm run cf:build` writes from the same `security-headers.mjs`. Pages that add a new third-party script, style or frame must add it to `LEGACY_CSP` in `security-headers.mjs`. The one addition so far is `https://player.vdocipher.com` in `script-src` (the player API, `v2/api.js`) and `frame-src` (the DRM player iframe) for lesson videos (security: not in legacy).
- **Lesson video:** lessons with `playback: "vdocipher"` get a one-time OTP from the API's `GET /lessons/{id}/playback` through a Server Action (`lib/playback-actions.ts`; the token stays on the server) and play in VdoCipher's iframe with a moving watermark (`components/lesson-video.tsx`). Content editors see a note instead of a player. Other videos keep `<video>` with downloads, picture-in-picture and the context menu off.
- **Private files in pages:** avatars, logos, thumbnails and attachments arrive as signed links that change with every response; pages render them with plain `<img>`/`<a>`/`<iframe>` (no `next/image`), and forms never send one back as a typed URL (`lib/signed-file.ts`).
- **Images:** the app doesn't use `next/image`, so no image optimisation is configured (no `IMAGES` binding). If it's added later, `/_next/image` serves the original file until an `images` binding (Cloudflare Images) is added to `wrangler.jsonc`.
- **Redirects:** they are built from `SITE_URL` (`lib/site-url.ts`).
- **Missing blog posts (404):** `proxy.ts` renders the site's 404 page by fetching `/site-404` from this app (`lib/self-fetch.ts`). In the Worker that goes through the `WORKER_SELF_REFERENCE` service binding: a Worker can't reach itself on `127.0.0.1`, and a fetch to `bodhiraai.com` from the Worker would skip the route and reach the zone's origin. Under `next start` it's `127.0.0.1:$PORT`.
- **The secret on API calls:** every call from the Next server code to the API sends `X-Proxy-Secret` (`lib/proxy-secret.ts`), and the API refuses calls without it. Any new `fetch` to the API must spread `proxySecretHeader()` (or `visitorHeaders()`).
- **Root files:** `favicon.png` was copied from legacy `public_html`. `robots.txt` and `sitemap.xml` are generated per request (`src/app/robots.ts`, `src/app/sitemap.ts`) from `SITE_URL` and the site API (SEO: not in legacy).
- **One canonical host (SEO, not in legacy; to set up at cut-over, nothing is deployed):** canonical, Open Graph, sitemap and JSON-LD URLs all use `SITE_URL` (`https://bodhiraai.com`), so every other address must answer a 301 to it:
  - **http → https:** Cloudflare dashboard → SSL/TLS → Edge Certificates → **Always Use HTTPS** on (a 301 at the edge, before the Worker). HSTS is already sent by production builds.
  - **www → apex:** a proxied DNS record for `www` (orange cloud) and a **Redirect Rule** (Rules → Redirect Rules): hostname equals `www.bodhiraai.com` → dynamic `concat("https://bodhiraai.com", http.request.uri.path)`, status **301**, preserve query string. Don't add a Worker route for `www` then; the rule answers first.
  - Check after cut-over: `curl -sI http://bodhiraai.com/about`, `curl -sI https://www.bodhiraai.com/about?x=1` → `301` with `Location: https://bodhiraai.com/about` (and `?x=1`).

## 6. Local check (no Cloudflare account)

```bash
cp .dev.vars.example .dev.vars   # local API on 127.0.0.1:4000, test secrets only
npm run cf:build                 # next build (webpack) + OpenNext bundle + _headers
npm run cf:preview               # wrangler dev in workerd, http://localhost:8787
npx wrangler deploy --dry-run --outdir dist --env=   # also --env production, --env staging
npm run test:worker
```

- Start the API on :4000. Without `APP_SECRET` it ignores `X-Proxy-Secret` and uses its built-in development file key, so signed links won't verify here. With the same `APP_SECRET` as `.dev.vars`, it checks the proxy header like production.
- Test files go into the local R2: `npx wrangler r2 object put bodhira-legacy/media/<path> --file <f> --content-type <type> --local`, and `"bodhira-private/<key>"` likewise. Sign a `/files` link with the same `APP_SECRET` (the file-urls key is derived from it; `signFileKey` in `worker/file-sig.ts`, or the API's signer).
- Signed links: `npm run test:worker` checks the signature rules, including a fixed vector the API must match: key `submissions/7/a b.pdf`, exp `2000000000`, secret `test-secret` → `AfIQbpO7Ovsv3aJJc4JbnUv2jkiWW8DtIC4XTA8fWG8`.
- `opennextjs-cloudflare preview` prints a warning that the internal Durable Objects "will not work in local development" while it fills the local cache; that comes from its cache step, not the dev server, where the tag cache and queue run (they're exported by `worker/index.ts`).

Checked on 2026-11-25 in `cf:preview` against the local API: the marketing pages, a blog post, `/login`, `/sitemap.xml`, `/robots.txt`, `/health`, `/up`, `/api/v1/ping` through the Worker, a missing post and an unknown URL (404 with the site's 404 page), signed-out redirects, security headers and CSP on pages and static files, no browser console errors; `/media` and `/files` from the local R2 with 200, 206 (normal and suffix), 416 past the end, 404 for invoices and missing keys, 405 on POST, 403 for a bad signature or no query; 413 for a 13 MB POST to `/contact`; `'use cache'` entries landing in the R2 cache and the tag cache Durable Objects in use; 60 concurrent page loads, all 200.

## 7. Known limits

- **Cache Components on Workers (risk; decide before cut-over):** the OpenNext build warns "Cache Components are not fully supported on Cloudflare yet" ([opennextjs-cloudflare#1318](https://github.com/opennextjs/opennextjs-cloudflare/pull/1318), open). Reported symptoms elsewhere: requests that hang ("Worker's code had hung", 500) after `revalidateTag`/`updateTag`, and background revalidation of partially prerendered pages failing. None of this showed in the local preview, but a Web Studio save (`updateTag('site')`) wasn't tested there (it writes to the database). Options: (a) rehearse saves on staging under load and ship if clean; (b) pin a release that includes that fix once it lands; (c) turn `cacheComponents` off, which means replacing `'use cache'`/`cacheTag` in `lib/site-api.ts` with `unstable_cache`/fetch tags and reworking the Suspense-based rendering (a large change); (d) serve the web app from the Node host (§8) and keep only the edge routing on Cloudflare.
- **`proxy.ts` on Workers:** Next 16's proxy runs in the Node.js runtime. OpenNext bundles it, with the warning "Node.js middleware support is experimental in cloudflare". It works in the local preview (redirects, the blog 404).
- **Upload size (decision needed):** Cloudflare caps request bodies by zone plan: 100 MB on Free and Pro, 200 MB on Business, 500 MB on Enterprise. Bodies above the plan's cap are refused with a 413 before the Worker runs. A Worker isolate also has **128 MB of memory**, and a Server Action holds an uploaded file in memory (`proxy.ts` buffers request bodies too), so large uploads through the web app's forms fail inside the Worker whatever the plan. Expect failures well below 128 MB (not measured: the local preview doesn't enforce the memory limit), so the 200 MB lesson videos (legacy limit) and 150 MB site videos don't fit. Options: (a) presigned direct-to-R2 uploads from the browser (the labelled improvement already in the runbook, §9), which removes both limits; (b) send large files from the browser straight to the API's upload endpoint under `/api/v1` (the Worker streams those bodies without buffering, but the plan's cap still applies); (c) cap videos at a size that fits until (a) lands; (d) run the dashboards' upload paths on the Node host. The per-path limits stay as before: `worker/body-limit.ts` answers 413 past 205 MB for `/content/chapters/*` and `/content/lessons/*`, 155 MB for `/cms/images`, 60 MB for `/cms/*` and assignment pages, 12 MB elsewhere (Next's own limit is 205 MB for the whole app). It checks `Content-Length` and also cuts off bodies that have none. Change these limits together with the API's upload rules (`bodhiraai-api/src/storage/upload-rules.ts`).
- **Worker size:** 12.4 MiB uncompressed, **1.9 MiB gzip** (2026-11-25; `wrangler deploy --dry-run` prints it). The limit is 3 MiB compressed on Free and 10 MiB on Paid.
- **CPU and duration:** Paid gives 30 s of CPU per request by default (configurable up to 5 min with `limits.cpu_ms`); waiting on the API doesn't count. Free gives 10 ms, too little for server rendering. Each request may make a limited number of subrequests (API calls, R2, Durable Objects); a page uses a handful.
- **Location:** the Worker runs in the colo nearest each visitor, and each page makes several calls to the API in AWS. If that latency shows, Smart Placement (`"placement": { "mode": "smart" }`) runs the Worker near the API instead. It's off for now (not in legacy).
- **Dashboard 404 status:** a missing dashboard page shows the 404 page but answers status 200. Blog posts answer a real 404.
- **Web sessions:** users signed in to the legacy website have to sign in again after cut-over. Mobile app tokens keep working.

## 8. Node hosting (Hostinger)

`npm run build` (`next build --webpack`) and `npm run start` (`next start`) work as before; nothing Cloudflare-specific runs there. `lib/self-fetch.ts` falls back to `127.0.0.1:$PORT`, and the Worker's routing (API proxy, R2 files, body limits) doesn't exist there: the host's own web server must provide it, or `LEGACY_URL` must point at a server that serves `/media` and `/cloud`. The Dockerfile was removed with the container setup, because neither target uses it.
